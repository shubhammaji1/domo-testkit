# Compatibility and security boundaries

- Node test processes only. jsdom's XHR and Node's native fetch are exercised. Browser service-worker installation, browser-mode Vitest, raw sockets, independent processes, all third-party HTTP clients, and fetch references captured before interception are unverified or outside this boundary. No claim of universal network isolation is made.
- One active interceptor per worker; overlapping same-worker kits reject. Separate workers can run in parallel. Concurrent tests sharing a kit also share state and must coordinate explicitly. Existing independent MSW servers in the same worker may conflict; use a dedicated test worker/configuration.
- Only the endpoint/version/method/query subsets in the compatibility matrix are implemented. Unsupported recognized requests are blocked, recorded and surfaced by the helper. Manual lifecycle users must call `assertNoUnhandledRequests` before clearing diagnostics.
- Request history and violation samples are bounded; their counts represent retained diagnostics. No suite pass counts are invented. Use Vitest reporters for test results and distinguish simulator tests, reference contract tests, application integration tests and live tests.
- Fixture metadata IDs may be arbitrary test identifiers. Generated IDs are predictable UUID-shaped values. Generated datastore/collection IDs are omitted. There is no backend UUID enforcement, BSON date conversion, security policy, sync, transaction or distributed concurrency emulation.
- Query behavior intentionally approximates only common JSON cases. Array traversal, full MongoDB null/array comparison semantics, mixed BSON types, `$date`, regex, sorting, aggregation and expression operators are not implemented. Query pagination is currently unsupported, even though list pagination is supported.
- AppDB v1 is opt-in. Its legacy specification entries are present in the current official YAML but excluded from the rendered reference. No live v1 request was made. Toolkit 2.3.0 is the only verified Toolkit version, and its bulk operations—including its single-ID delete method—remain unsupported.
- Dataset legacy `mapping` has an explicit adapter for the supported entry shape; broader historical shapes are unverified. Collection mappings do not simulate Domo document-level filters or manifest publish behavior.
- Delays use the current global timer APIs. TestKit cancels its own pending delays but does not install or restore caller-owned fake timers. `dataset:timeout` is a delay scenario; actual timeout rejection belongs to the caller's abort/client implementation.
- Redaction protects captured diagnostics. Fixture HTTP responses deliberately include fixture content; values in arbitrary error strings from third-party clients or application snapshots cannot be guaranteed safe. Use synthetic fixtures and configure additional secrets before opting into body capture.
- Domo Doctor detection is informational only. No stable structured diagnostic integration is claimed. The CLI checks JSON fixture/configuration data and dependency availability; it does not execute tests or validate a full Domo manifest during `check`.
- The package is ESM only. React, jsdom and Toolkit are development/example dependencies and are not required by the core. Only MSW 3 and Vitest 5 are declared supported. The main entry does not import Vitest.
- GitHub CI has passed complete verification on Windows with Node 22/24/26, and tests, coverage and builds on Linux/macOS with those Node versions. A Unix npm-symlink CLI launch bug was then found in the consumer smoke step. Its local real-path fix and regression check require a new full matrix run before release. Local execution uses Windows Node 22.22.
- No publication, live Domo authentication, telemetry or live integration feature is included. A passing mock test is not evidence of correct live deployment or authorization.
